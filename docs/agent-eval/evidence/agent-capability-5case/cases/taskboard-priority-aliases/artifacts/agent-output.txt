# sort_by_priority 优先级别名支持 — 技术方案

## 1. 需求理解

在不改变现有 API 形状的前提下，扩展 `taskboard.tasks.sort_by_priority` 的优先级识别能力：

| 需求点 | 含义 | 期望行为 |
| --- | --- | --- |
| 别名 | `urgent` 等价 `high`，`backlog` 等价 `low` | `urgent` 与 `high` 排在同一档，`backlog` 与 `low` 排在同一档 |
| 大小写不敏感 | `HIGH` / `Urgent` / `Backlog` 均视为已知级别 | 与全小写走同一映射 |
| 相同级别稳定 | 同一档内保持输入相对顺序 | 需要排序稳定，`sorted` 本身稳定，关键字不得引入额外次序扰动 |
| 未知级别规整 | 未知优先级排在所有已知级别之后 | 未知档位键值大于任何已知档位；未知项之间也保持输入相对顺序 |
| 缺失 priority | 缺少 `priority` 字段视作未知 | 排在末尾，不抛异常 |

现状实现（`taskboard/tasks.py` 第 28–32 行）已有 `order = {"high": 0, "medium": 1, "low": 2}` 且已做 `str(...).lower()` 与默认值 `99`，即大小写与未知兜底逻辑已具备，仅缺 `urgent` / `backlog` 别名；对应测试 `tests/test_sort_by_priority.py` 期望 `[2, 4, 5, 1, 3]`，当前实际输出 `[4, 5, 1, 2, 3]`，失败点正是别名未生效。

本次范围严格限定为两个文件：`taskboard/tasks.py`、`tests/test_sort_by_priority.py`。

## 4. 具体实施步骤

**步骤 1：扩展映射表（`taskboard/tasks.py`）**

在 `sort_by_priority` 内把 `order` 由 3 项扩展为 5 项：保留 `high`/`medium`/`low`，额外加入 `urgent → 0` 与 `backlog → 2`，使别名与主名同档。档位数字保持不变，避免影响 `medium` 的相对位置和未知兜底比较关系。

**步骤 2：保持归一化与兜底逻辑**

保留当前 `str(task.get("priority", "")).lower()` 的取值方式与 `order.get(..., 99)` 的兜底写法，不引入新分支。核心逻辑可概括为（4 行伪代码）：

```
order = {"high": 0, "urgent": 0, "medium": 1, "low": 2, "backlog": 2}
def rank(task):
    name = str(task.get("priority", "")).lower()
    return order.get(name, 99)
return sorted(tasks, key=rank)
```

要点：兜底值必须严格大于 2，保证未知档位排在已知之后；使用内置 `sorted`（稳定排序）且 `key` 只返回档位、不混入索引或原值，保证同档与未知项的相对顺序不被破坏；不修改入参、不复制或改写任务字典（与 `filter_by_status`/`search_tasks` 的既有约定一致）。

**步骤 3：更新函数文档字符串**

把 `docstring` 从“ordered by priority while preserving equal-priority order”补充为同时说明别名、大小写不敏感与未知级别后置，便于后续维护者理解契约。

**步骤 4：扩展测试（`tests/test_sort_by_priority.py`）**

保留现有用例 `test_priority_sort_keeps_equal_and_unknown_priorities_stable`（它同时覆盖了别名、缺失字段与未知值），并按需求补充独立用例：

| --- | --- | --- |
| 别名等价性 | `urgent` 与 `high`、`backlog` 与 `low` 同档 | 混排后输出顺序等价于把别名替换为主名后的结果 |
| 大小写不敏感 | `HIGH` / `Urgent` / `Backlog` / `MEDIUM` | 与全小写输入产生相同顺序 |
| 同档稳定性 | 多个 `high` 与多个 `urgent` 交错的输入 | 输出 id 顺序与输入出现顺序一致（用计数器而非集合比较） |

## 6. 风险点和需要用户确认的事项

| 风险 / 待确认点 | 说明与建议 |
| --- | --- |
| 未知档位是否统一为同一档 | 现方案让所有未知值（含缺失、`None`、数字）落到同一兜底档并保持输入相对顺序，即“未知之间不再按字符串比较”。若期望未知值之间另有排序规则，需要新增约定 |
| 大小写归一化是否覆盖异常输入 | 采用 `str(...)` 兜底可避免 `None`/数字导致 `AttributeError`，但也会把 `None` 变成字符串 `"none"`；语义上仍归为未知，通常符合预期，需确认不要求抛错 |
| 是否允许新增 `critical` 等更多别名 | 需求只给了 `urgent`/`backlog`。若评测 oracle 含其他别名或同义词，需明确扩展列表 |
| 空白字符处理 | 当前不做 `strip()`。若输入可能带首尾空格（如 `" high"`），是否也应视为已知级别需要确认 |
| 是否有隐藏 oracle 比对顺序 | `cases/README.md` 说明评测方另有独立 oracle。若其期望未知值之间也有确定次序，本方案的“统一兜底档”可能出现偏差 |
| 基线本身已有失败用例 | `test_filter_by_status.py` 与 `test_search_tasks.py` 现存 4 个失败与本任务无关，不在本次修改范围。确认是否要求顺带修复（本方案默认不修） |
