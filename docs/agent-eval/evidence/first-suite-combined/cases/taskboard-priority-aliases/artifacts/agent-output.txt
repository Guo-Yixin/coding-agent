# sort_by_priority 优先级别名支持 — 技术方案

## 1. 需求理解

当前 `sort_by_priority` 只看 `high / medium / low` 三个字面量，其余（包括 `urgent`、`backlog`）一律落到未知名次 99，排在全部已知级别之后。

目标语义（本次要改成的）：

| 输入 priority | 归一后级别 | 排序名次 |
| --- | --- | --- |
| `high`、`urgent`（忽略大小写） | 高 | 0 |
| `medium`（忽略大小写） | 中 | 1 |
| `low`、`backlog`（忽略大小写） | 低 | 2 |
| 其它任意值 / 缺失 / 空串 | 未知 | 3 之后（排在所有已知级别之后） |

四个硬性约束：

1. **别名等价**：`urgent` ≡ `high`，`backlog` ≡ `low`。
2. **大小写不敏感**：`URGENT`、`High`、`BackLog` 都要被识别（现有实现已有 `.lower()`，要保持）。
3. **稳定性**：同一级别内部保持输入相对顺序（Python `sorted` 本身稳定，前提是 key 不引入随机/次要不稳定因素）。
4. **未知级别**：同级别内保持原有相对顺序，且整体排在所有已知级别之后。
5. 附带：缺失 `priority` 字段不能抛异常（现有实现用 `.get(..., "")` 已覆盖），不应修改输入列表。

一个重要的语义推论：由于 `urgent` 与 `high` 名次相同，它们**互为同级**。因此 `[urgent#1, high#2]` 排序后仍是 `[urgent#1, high#2]`，不会把 high 全部提前。这一点必须在实现和测试中同时体现。同理 `low` 与 `backlog` 互为同级。

## 3. 数据结构、接口或页面变化

- **对外函数签名不变**：`sort_by_priority(tasks: Iterable[Task]) -> list[Task]`，无新增参数。
- **数据结构不变**：仍是 `Task = dict[str, Any]`，仍返回 `list[Task]`，新列表、不修改输入。
- **唯一变化是内部映射表**：从 3 个键扩到 5 个键（或等价的双层归一逻辑），把 `urgent→0`、`backlog→2` 显式登记。
- 可选但推荐的内部重构：新增一个模块级私有常量（例如 `_PRIORITY_ORDER` 字典）承载名次表，`sort_by_priority` 只负责取值 + 归一 + 排序。这样别名规则只有一处来源，便于后续扩展。它不进入 `taskboard/__init__.py` 的 `__all__`，不属于公开 API。
- 未知名次的选择：现实现用 `99`。可保留 `99`，或用 `len(_PRIORITY_ORDER)` 表达语义。关键是只要是**同一常量**，未知项之间 key 相等，稳定性由 `sorted` 保证。
- 无页面/接口/接口字段变化；`taskboard/__init__.py` 与 `__all__` 不需要同步。

核心逻辑（3 行伪代码，说明思路而非最终实现）：

```
order = {"high": 0, "urgent": 0, "medium": 1, "low": 2, "backlog": 2}
unknown = len(set(order.values()))          # 或固定的 99
key = lambda task: order.get(str(task.get("priority", "")).lower(), unknown)
return sorted(tasks, key=key)
```
