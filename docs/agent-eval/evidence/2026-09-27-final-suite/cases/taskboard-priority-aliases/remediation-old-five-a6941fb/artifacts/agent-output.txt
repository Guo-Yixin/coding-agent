# sort_by_priority 优先级别名支持 — 技术方案

## 1. 需求理解

用户要求在 `taskboard/tasks.py` 的 `sort_by_priority` 上补齐优先级归一化与排序语义：

| 编号 | 需求 | 判定标准 |
| --- | --- | --- |
| R1 | 别名字面量 | `urgent` 等价 `high`（最高），`backlog` 等价 `low`（最低） |
| R2 | 忽略大小写 | `HIGH`、`High`、`high`、`Urgent` 得到同一档位 |
| R3 | 同一优先级稳定 | 同档位任务保持输入相对顺序（Python `sorted` 天然稳定，需保证 key 不引入二次比较） |
| R4 | 未知优先级稳定且排在最后 | 未知值互相之间保持原相对顺序，且整体排在所有已知级别之后 |
| R5 | 缺失 priority | `task.get("priority")` 为 `None` 或键不存在时归入未知档，不抛异常，排最后 |
| R6 | 测试覆盖 | 扩展 `tests/test_sort_by_priority.py`：别名、大小写、相同级别稳定性、缺失 priority |
| R7 | 改动范围 | 只允许修改 `taskboard/tasks.py` 与 `tests/test_sort_by_priority.py` |

当前实现（`taskboard/tasks.py:28-32`）已把已知档位限定为 `{"high":0, "medium":1, "low":2}`，未知档位用 `99` 兜底，并且已经调用 `.lower()` —— 也就是说 **R2/R3/R4/R5 已经基本满足**，真正缺失的是 R1 的别名映射（`urgent` 当前落到 99 未知档、`backlog` 也落到 99）。现有可见测试 `tests/test_sort_by_priority.py` 恰好断言了旧行为 `[2, 4, 5, 1, 3]`（`urgent` 与 `backlog` 被当成未知），实施后该断言需要同步更新为新语义。

仓库 `cases/README.md` 中该 case（`taskboard-priority-aliases`）的验收描述为 “Priority aliases, stable ordering, explicit tests for edge cases”，与上述理解一致；评测方还会在候选工作区之外运行独立 oracle，因此实现必须按语义写正确，而不只是让可见测试变绿。
