# anti-patterns.md — 视觉禁飞区

> **强制阅读。** 每次生成或修改界面之前读一遍。
> 这份清单比"应该怎么做"更有效 —— 因为它列的都是**具体动作**，
> 而"要有高级感"不是动作，无法执行。
>
> 增补规则：每次验收发现新问题时，先往这里加一条，再改代码。

---

## 一、颜色

### AP-01 新增 `:root` 块或新的变量定义处

- **长什么样**：`tokens.css` 里有一个 `:root`，另一个文件（或同文件后半段）又写了一个。
- **为什么坏**：多个 `:root` 会**静默覆盖**，最终生效的值取决于文件加载顺序 ——
  这不是设计，是事故。真实案例：某项目 3 个 `:root` 块，`--accent-strong` 被覆盖成
  新值，但旧值仍作为字面量出现在 3 处，同一语义两种颜色共存。
- **正确做法**：全项目只有一个 `:root`（在 `tokens.css`）。改值就改那一个。
- **机器可查**：`audit-css.mjs` 的 `:root` 块数，阈值 1。

### AP-02 写颜色字面量

- **长什么样**：`color: #356b63;` / `background: rgba(47,47,47,0.07);`
- **为什么坏**：字面量无法被检索、无法被统一修改。每一次写新字面量，
  都是"重新发明一个值"—— 7 个几乎一样的绿色就是这么来的。
- **正确做法**：`color: var(--c-text-secondary);`
- **例外**：仅当颜色是**内容本身**（如用户头像的哈希色、SVG 图表数据色）。
  必须加注释说明为什么不能用 token。
- **机器可查**：stylelint `declaration-property-value-disallowed-list`。

### AP-03 为同一个语义造第二个 token

- **长什么样**：已经有 `--c-text-secondary` 了，又加 `--muted`、`--ink-muted`、`--text-dim`。
- **为什么坏**：三个名字一个意思，用哪个全凭当轮心情 → 漂移。
- **正确做法**：先 grep 现有 token 名，找语义最接近的复用。真的语义不同才新增，
  并在 `tokens.css` 注释里写清"和 X 的区别是什么"。

### AP-04 引入第二套灰

- **长什么样**：项目里同时有 Tailwind 的 `#94a3b8/#64748b/#475569` 和自定义的 `#9aa39f/#a0aaa5`。
- **为什么坏**：两套灰的色温不同，并排出现时**整体看起来发脏**，
  但单独看每个值都很正常 —— 所以极难自查。
- **正确做法**：只用 `tokens.css` 里的中性色阶。用了组件库就把它主题变量
  映射到自己的 token 上，不要两套并存。

### AP-05 混用多个阴影基色

- **长什么样**：`rgba(0,0,0,.05)`、`rgba(38,50,56,.07)`、`rgba(15,23,42,.06)` 混用。
- **为什么坏**：阴影是最容易露馅的地方 —— 基色不同的阴影在浅色底上
  呈现不同的偏色，看起来"脏"且不统一。
- **正确做法**：所有阴影一个基色，只改 alpha。

## 二、尺寸与节奏

### AP-06 间距/字号/圆角写裸 px

- **长什么样**：`padding: 13px 19px;` / `font-size: 14px;` / `border-radius: 11px;`
- **为什么坏**：真实案例 —— 某项目 1313 行 CSS 里只有 **31 次 `var()`**，
  约 97% 是硬编码；产出 21 种圆角、19 种字号、16 种近白背景。
  **不是因为某个值错了，而是因为没人负责"不许发明新值"。**
- **正确做法**：`padding: var(--space-12) var(--space-24);`
- **例外**：`1px` 边框线宽、`100%`/`50%` 几何值、`1px` 定位微调。
- **机器可查**：stylelint `declaration-property-unit-disallowed-list`。

### AP-07 发明中间档位

- **长什么样**：已经有 12px 和 13px，又写 `font-size: 12.5px` 或 `10.5px`；
  圆角已经是 10 和 12，又写 11。
- **为什么坏**：人眼分辨不出 11 和 12 的差别，但**能**察觉到"这个界面很乱"。
  中间档只增加噪音，不增加信息。
- **正确做法**：要么用现有档位，要么承认现有档位错了 —— 改 token，
  不要在调用点打补丁。

### AP-08 字号分布倒挂

- **长什么样**：12px 用了 32 次，13px（正文基准）只用了 14 次；同时存在 8px 和 9px。
- **为什么坏**：说明没有正文基准，每次都是"我觉得这里小一点"。
  标注的是无意义的细节（8px 没人读得清），真正需要层级的正文反而没有体系。
- **正确做法**：先定正文基准（密集工具界面 13px / 阅读型 15~16px），
  其余档位相对它分布，且相邻档差 ≥2px。

### AP-09 圆角与元素大小不匹配

- **长什么样**：28px 高的按钮用 `border-radius: 16px`；大卡片用 `4px`。
- **为什么坏**：圆角应该是"元素尺度的函数"，不是自由参数。
  小元件配大圆角会显得笨拙，大容器配小圆角会显得廉价。
- **正确做法**：控件 `--radius-sm`、容器 `--radius-md`、大容器/弹层 `--radius-lg`。

## 三、迭代方式（最隐蔽的一类）

### AP-10 追加 `/* refinement */` 覆盖块

- **长什么样**：
  ```css
  /* Composer refinement: context, task input, and explicit actions. */
  .composer { ... }   /* 第三次定义 .composer */
  ```
- **为什么坏**：**这是 CSS 膨胀的头号来源，也是这类界面最该禁止的一条。**
  每次说"改成 X"，AI 就在文件末尾追加一段覆盖样式而不是修改原规则。
  真实案例：某文件 453 条规则只覆盖 387 个选择器，66 条是重复声明；
  文件里的注释就是一部迭代史，6 段 refinement 层层覆盖。
  后果：改一处要读三处，删一段不知道会不会塌，新人无法接手。
- **正确做法**：**改原规则。** 找到定义该选择器的那一处，直接改。
  确实需要覆盖时（媒体查询、状态修饰符）必须由选择器本身表达，不是靠顺序。
- **机器可查**：`audit-css.mjs` 的**冗余声明（同属性重复声明）**数，阈值 0 ——
  同一选择器下同一个属性被声明多次，后一条必然覆盖前一条，删掉前一条不改渲染。
  > 「同一选择器分散在多块」已降级为**提示项**，不再是硬门：各块声明的属性互不
  > 重叠时它并不冗余；要把它归零只能合并块，而合并会把声明搬到文件更靠后处、
  > 从而改变它与其它同特异性选择器之间的先后关系 —— 有渲染风险，不适合当硬门。

### AP-11 "顺便优化"

- **长什么样**：让它改按钮颜色，它顺手把圆角、间距、另一个组件的字体也调了。
- **为什么坏**：单次改动不可审查、不可回滚；更重要的是 —— 这些"顺手"的改动
  没有经过你确认，累积起来就是无人负责的漂移。
- **正确做法**：提示词里显式写：
  > 只做我要求的事。发现其他问题请**单独列出来**，不要顺手改。
  > 每一条改动都要能对应到我要求里的某一句话。

### AP-12 一次改多个维度

- **长什么样**："把界面改好看一点，顺便调下间距和配色。"
- **为什么坏**：多个维度同时变，出问题时无法定位是哪个维度导致的；
  也无法判断哪个维度变好了。而且 AI 在多个维度上同时"创作"，
  每个维度都更容易失控。
- **正确做法**：一次只改一个维度（对齐 → 间距 → 灰度 → 圆角 → 颜色）。
  改完截图看一下，再动下一个。

### AP-13 用形容词下需求

- **长什么样**："让它看起来更高级 / 更现代 / 更清爽。"
- **为什么坏**：形容词没有可执行的落点。AI 会各自解释"高级"，
  同一句话在两个会话里产出两种完全不同的界面。
- **正确做法**：给数值或给参照图。
  - 数值："行高从 1.4 提到 1.6"、"主按钮用 --c-accent"
  - 参照："看 reference/linear-inbox.png，取它的列表行高和分割线用法"

### AP-14 用同一个长会话连续做界面

- **长什么样**：在同一个 session 里从第一个组件聊到第十个页面。
- **为什么坏**：AI 会**复制自己早期的输出**（复制偏差）——包括早期的坏决定。
  越到后面越像前面的，而不是越像规范。
- **正确做法**：一个界面开一次会话，但每次都带上同一份 `DESIGN.md`。
  规范活在仓库里，不活在对话历史里。

## 四、交互状态

### AP-15 只有正常态

- **长什么样**：页面只有"有数据"的样子。空列表是一片白，请求失败是控制台报错。
- **为什么坏**：空态和错态占用户实际看到的时间**不低**（新用户第一次打开就是空态）。
  只做正常态的界面，对真实用户而言是半成品。
- **正确做法**：每个页面的状态矩阵（正常/加载/空/错误/超长内容/无权限）全部实现。
  **先做空态和错态，再做正常态** —— 顺序反了就永远补不上。

### AP-16 缺失焦点态 / 禁用态 / hover 态

- **长什么样**：输入框 tab 进去看不出来；禁用按钮和可用按钮长得一样。
- **为什么坏**：键盘用户无法定位；禁用态不可辨识会让人反复点击。
- **正确做法**：每个交互原语必须覆盖 `default / hover / focus-visible / disabled`。
  焦点态用 `outline`，**禁止 `outline: none` 而没有替代方案**。

### AP-17 同行控件视觉重量不一致

- **长什么样**：一行里下拉框 32px 高、输入框 36px 高、按钮 28px 高；
  或者一个是实心一个是描边一个是纯文本，却代表同一级操作。
- **为什么坏**：这是"看起来不专业"最直接的原因，且单看每个控件都很正常。
- **正确做法**：同行控件高度取自同一档 `--control-h-*`；
  同一层级的操作用同一 variant。**先把这行的控件高度对齐，再谈美观。**

### AP-18 把控件状态当正文写进页面

- **长什么样**：Hero 大标题下面写一行 `独立会话仓库上下文模型代号`。
- **为什么坏**：模型名是下拉框的**状态**，不是文案。它既重复了 composer 里已有的信息，
  又因为混在正文里而语义不明（读者不知道这串字符是什么）。
  这是**信息架构错误**，不是样式错误 —— 调字号救不了它。
- **正确做法**：状态归属它所属的控件。确实要在正文里提及时，
  用完整的自然语言句子，并放在它服务的那句话旁边。

### AP-19 一个界面多个主色互相打架

- **长什么样**：logo 深绿、主按钮深绿、状态徽标亮青、发送按钮中性灰。
- **为什么坏**：眼睛找不到"哪个是品牌色"。主色的作用是建立识别，
  分裂成两三个之后就不再是主色了。
- **正确做法**：一个主色。需要区分的状态用语义色（success/warning/danger），
  不要另造一个品牌色。

## 五、可维护性

### AP-20 组件直接发请求

- **长什么样**：`onMounted(async () => { const r = await fetch('/api/...') })`
- **为什么坏**：接口一改要改 N 个组件；无法统一处理错误/鉴权/加载态；
  无法在没有后端时开发界面。
- **正确做法**：唯一网络出口（`api/client.ts`），组件只调 typed 函数。
  契约层先行 + mock，见 `references/bootstrap.md`。

### AP-21 `!important`

- **长什么样**：`color: var(--c-text) !important;`
- **为什么坏**：几乎总是 AP-10 的后遗症 —— 因为重复规则打架，只好用 `!important` 压。
  一旦开始，就再也停不下来。
- **正确做法**：修根因（删掉重复的旧规则），不要加 `!important`。

### AP-22 内联 `style="..."`

- **为什么坏**：绕过了所有 token 和审查；无法被 lint 覆盖。
- **正确做法**：用 class 或原语组件的 props。
- **例外**：真正动态计算的值（如进度条宽度 `style="width: 42%"`），
  且必须只涉及几何量，不涉及颜色/字体。
