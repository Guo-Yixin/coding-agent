# CODING 默认代码审查规则

> 这些规则用于第一版 Reviewer 子 Agent。目标是发现可能导致真实故障、权限问题、安全风险或测试回归的问题。
> 不要把纯风格偏好、无明确风险的命名建议作为 finding。

## 1. 审查原则

- 只审查本次 diff 或 Pull Request 相关变更。
- 优先指出会造成线上故障、数据错误、权限绕过、安全泄露、测试失败的问题。
- finding 必须包含文件路径、行号、严重级别、问题标题、具体风险和修复建议。
- 如果无法定位到真实变更文件或真实变更行，不能记录为行级 finding，可放入总结中的“非阻塞观察”。
- 输出必须使用中文；代码标识符、文件路径、命令、API 名称可以保留英文。

## 2. 严重级别

| 严重级别 | 使用场景 |
|---|---|
| `critical` | 会导致严重安全漏洞、数据破坏、核心流程完全不可用，或必须阻止合并 |
| `high` | 很可能导致功能错误、权限绕过、测试失败、兼容性破坏 |
| `medium` | 存在明确风险，但影响范围有限，建议合并前修复 |
| `low` | 可维护性、边界体验、日志可观测性等非阻塞问题 |
| `info` | 纯信息提示，不作为阻塞问题 |

## 3. 通用正确性规则

- 新增分支逻辑必须覆盖成功、失败、空数据、重复数据等基本路径。
- 修改已有函数时，确认所有调用点的参数和返回值仍然兼容。
- 不允许因为新增功能破坏已有 API 的返回结构，除非需求明确要求。
- 不允许吞掉异常后继续返回成功状态。
- 不允许把测试失败、命令失败、API 失败伪装成成功。

## 4. Python / FastAPI 规则

- 路由函数必须明确处理参数缺失、参数类型错误和业务数据不存在。
- 涉及鉴权时，不能只依赖前端控制，后端必须校验。
- 涉及文件路径时，必须保证路径在工作区或项目目录内，不能允许任意绝对路径。
- SQLite 写入必须考虑提交、回滚、连接关闭和并发锁。
- 后台任务异常必须写日志，并更新任务状态，不能让前端一直显示 running。
- 测试中不要依赖本机绝对路径；如确实需要工作区路径，应通过环境变量或临时目录注入。

## 5. Web / 模板规则

- 模板中展示用户输入或外部数据时，要避免 XSS 风险。
- 表单提交必须和后端字段一致。
- 页面新增入口必须能从现有导航或流程访问。
- 错误提示要能让用户理解原因，不要只显示原始堆栈。

## 6. 数据和权限规则

- 用户、角色、部门、权限等关系变更必须保证数据一致性。
- 一个用户只能属于一个部门、一个角色等约束，必须在后端落地，不能只靠前端。
- 删除操作必须考虑关联数据。
- 权限校验失败应返回明确错误，不能继续执行目标操作。

## 7. 安全规则

- 禁止把 `.env`、token、私钥、API key 写入日志、前端事件、PR 评论或长期记忆。
- 禁止把 Gitee token 拼接到 remote URL。
- 禁止将用户输入直接拼进 SQL、shell 命令或文件路径，避免 SQL 注入、命令注入和路径穿越。
- 禁止绕过 LocalShellBackend 的工作区边界。

## 8. 测试规则

- 新增业务能力应至少有成功路径测试和失败路径测试。
- 修改数据存储方式时，必须保留旧功能回归测试。
- 修复 bug 时，应新增能复现该 bug 的测试。
- 如果无法运行全部测试，必须说明原因，并运行最小相关测试。

## 9. Gitee / 跨平台兼容规则

- Git 命令认证应使用 askpass 或受控环境变量，不要把 token 写入命令文本。
- 路径处理必须兼容 Windows 反斜杠、Linux 正斜杠和虚拟路径 `/projects/...`。
- Gitee API 返回重复 PR 时，应复用已有 PR，不要直接失败。
- 日志和前端输出中的 URL 或错误文本必须脱敏。
